2. この単元の教材方針

この単元の主題は「Kotlinという言語を初めて書く」ことです。プログラミングの入門ではありません。受講生はすでに Java と Swift を書けるので、同じことを Kotlin ではどう書くか、そこで何が変わったかに集中させます。教科書の各STEPには、Java か Swift（または両方）との比較を必ず置いています。

Kotlinパートを、単元に分けずに1つにした理由

Kotlinの文法は、K01HelloKotlin という単元1つ、プロジェクト1つ、教科書1冊で、6コマかけて進めます。「変数」「Null安全」「クラス」…と単元を分け、そのたびに新しいプロジェクトを作らせる形にはしていません。理由は3つです。

  • ウィザードの操作で時間が消えるからです。1コマで書くコードは十数行です。それなのに毎回プロジェクトを新規作成させると、90分のうち15〜20分が新規プロジェクトの操作と最初のビルド待ちに消えます。比較に使う時間がそのぶん減ります。
  • 前に書いたコードを見返せるからです。同じプロジェクトに ex01、ex02 …と並ぶので、「先週の val の行と見比べて」と、画面の中だけで指示できます。別プロジェクトだと、開き直す操作から説明することになります。
  • 前年度の資料と同じ形だからです。前年度も1つの HelloKotlin プロジェクトに、節ごとのファイル（Main01、Main02 …）を足していく形でした。今年はファイルの代わりに src/exNN/ のパッケージを足します（「7. 前年度の資料（PDF）との対応」）。

この決め方の結果として、2コマ目以降は「新しいプロジェクトを作る回」ではなく「同じプロジェクトを開き直す回」になります。1コマ目の STEP 02（プロジェクトの新規作成）は、6コマで1回だけです。ここで作った場所（Documents/Kotlin/K01HelloKotlin）を学生が言えるようにしておくことが、2コマ目以降の授業時間を守ります。

方針理由授業での扱い
Kotlinパートを 単元1つ・プロジェクト1つ・教科書1冊にまとめ、6コマかけて ex01〜ex11 を進める1コマ十数行のコードのために毎回プロジェクトを作ると、90分のうち15〜20分がウィザードの操作に消える。前の回のコードが同じプロジェクトに並ぶので見返せる。前年度の資料も1プロジェクトにファイルを足す形だった。プロジェクトの新規作成は1コマ目のSTEP 02の1回だけ。2コマ目以降は、最近開いたプロジェクトの一覧から K01HelloKotlin を開かせ、src に次のパッケージを足させる。
各STEPに Java / Swift との比較を必ず置く受講生は概念を知っていて、知らないのは書き方だけ。概念から説明すると、知っている話を聞く時間になり、90分が足りなくなる。前年度の資料も同じ方針で書かれている。教科書の比較ブロックを読ませたあと、「Javaなら何行になるか」を口で言わせる。教員は違いの理由（なぜKotlinはそう決めたか）を1文で足す。
導入の最初だけ Kotlin Playground を使い、STEP 02からは IntelliJ IDEA に移る環境構築で最初の10分を失うと、比較に使う時間がなくなる。ブラウザなら全員が同じ画面で1行目を動かせる。一方でPlaygroundはコード補完が効かず実行も遅いので、学習の本体には向かない。詳しくは「4. Playground と IntelliJ IDEA の使い分け」を参照。Playgroundは10分で切り上げる。
ビルドシステムに Gradle ではなく IntelliJ を選ばせるこの単元で見せたいのは val / var と型推論の差分だけ。Gradleを入れると、設定ファイル・同期待ち・依存関係の説明が増え、比較の時間を食う。できあがるフォルダの形も変わり、以降6コマぶんの画面と手順が教科書と食い違う。Gradleは後半のAndroid系の単元で扱う。STEP 02の表で ビルドシステム を IntelliJ と指定している。ここは学生が最も間違えやすい場所なので、机間巡視で最初に見る（「3. 90分の進め方」の STEP 02、「6. 机間巡視の確認項目」）。HELPにも「ビルドシステムに IntelliJ がない」の行を置いている。
「サンプルコードの追加」をONのまま作らせ、自分でコードを書く前にまず1回実行させる動く状態から始めれば、あとで動かなくなったときに疑う場所が自分が書き換えた行だけになる。空のプロジェクトから始めると、JDKの選択・実行構成・書いたコードのどれが原因かを切り分けられず、質問が「動きません」で止まる。ウィザードが作る Main.kt は、fun main() がクラスの外にあるKotlinの形そのものでもある。STEP 02で、まず src/Main.kt をそのまま実行させ、コンソールに出力が出ることを全員で確認する。そのあと Main.kt を消し、ex01 パッケージと main.kt を作らせる。
学生にも src/ex01/ パッケージを作らせ、package ex01 を書かせるリポジトリの完成プロジェクト K01HelloKotlin は、6コマぶんの演習を src/exNN/ で分ける構成にしている。学生の手元も同じ形にしておくと、見本と1対1で比べられ、行き先を言葉で指定できる。2コマ目以降に ex02、ex03 …を足していくときも、同じ操作の繰り返しで済む。STEP 02で作らせる。Javaのパッケージと同じ考え方だと1文で伝え、Kotlinではフォルダ構成と一致させなくてもよいという細部には触れない。
val の再代入エラーを、STEP 05の練習Bでわざと出させるJavaの final、Swiftの let を知っているので、説明より「自分の画面に出たエラー文」のほうが対応付けが早い。STEP 03は val と var の書き分けに使い、エラーを出すのは書き分けを一度書いたあとにする。STEP 05の練習Bで number1 = 5 を書き足させ、'val' cannot be reassigned を確認させてから消させる。あわせて「val は再代入禁止であって、中身が変わらない保証ではない」ことを口で言う。
型を明示せず（val number1: Int = 1 と書かせず）、型推論のままにする完成コード K01HelloKotlin/src/ex01/main.kt がその形であり、教材と完成版をバイト単位で一致させているため。Swiftの型推論を知っている受講生には、書かないほうが差分が見えやすい。STEP 04で「名前にマウスを重ねると、決まった型が出る」と案内し、Swiftと効き方が違う場面（Float）だけを取り上げる。
コメント // Double / // Float を完成コードに残す完成プロジェクトの書き方をそのまま教材にしているため。型推論に任せた行がどの型になったかを、後から読み返す手がかりになる。STEP 04で「型推論の結果をコメントで補っている」とだけ説明する。KDocの書き方は扱わない。

この1コマ目で意図的に扱わないこと

「あとの回で扱う」と書いたものは、教科書の本文からは案内しません（まだ書かれていないSTEPへ本文で送らない方針のため）。教員が口頭で「それは次回」と言う用途の表です。行き先はどれも同じ単元・同じ教科書の、あとの回のSTEPです。別の単元に移るわけではありません。

扱わないこと理由どの回で扱うか
Null安全（? / ?. / ?: / !!）受講生はSwiftのオプショナルを知っているので、比較の題材としては良いが、1コマに入れると差分が2つになる。今回の値はすべてnullにならないので、使わない記号を先に見せない。ex02（2コマ目以降）
関数を自分で作る（fun の定義・引数・戻り値）今回書く fun は main だけ。引数の書き方（引数名: 型）はSwiftと同じで、戻り値の書き方だけがJavaと違う。ここは1つのSTEPを取って比較したい。ex03
条件分岐と繰り返し（if / when / for）出力が4行で固定のため、なくても完成する。Javaとほぼ同じ書き方なので、説明の優先度も低い。ex05 / ex06
クラス・プロパティ・アクセサ（get() / set() / field）「値に名前を付ける」ところに集中させるため。プライマリコンストラクタと new 不要は、Javaとの差が大きく、1コマ分の題材になる。ex04 / ex08
バイトコードの確認（Show Kotlin Bytecode → Decompile）この回にはアクセサも自動生成コードもなく、見ても差分が現れない。バイトコードは「プロパティにアクセスするとアクセサメソッドが呼ばれている」ことを確かめるための道具なので、プロパティを扱う回に置く。ex04（前年度資料の 7.4）
data class・スマートキャスト・拡張関数今回はクラスを作らない。拡張関数はSwiftの extension と同じ発想なので、比較の題材としてまとめて扱いたい。ex09 / ex07
コレクション（List / map）・by lazy値が4つしかないため、まとめて扱う必要がない。ex10 / ex11
Javaのプリミティブ型とラッパー型の詳細（int と Integer、オートボクシング、Kotlinの Int が何にコンパイルされるか）Kotlinでは Int と書くだけで、使い分けの判断が要らない。「Java側の事情がどう消えたか」を語り始めると、今日の主題である書き方の差分から離れ、実行時の話に入ってしまう。Java相互運用を扱う場面（この15コマでは扱いません）
Long / Short / Byte / Char / Boolean などの網羅完成コードにない型は出さない方針のため。型の一覧はJavaで学習済みで、Kotlinでも名前が違うだけ。使う3つ（Int / Double / Float）に絞り、リテラルの書き方の差（3.0f）だけを見せる。必要になった単元
文字列テンプレート（$name）と String の操作1コマ目の新概念を1つに保つため。$ を足すと「文字列の中と外」という別の話が増える。ウィザードのサンプルコードには $i が出てくるが、消すので説明しない。ex02 以降
Gradle・依存ライブラリの追加コンソールアプリに追加するライブラリがない。ライブラリは必要なときだけ足す。Android系の単元（A01〜）
Unit Test完成プロジェクトにUnit Testは書かない方針のため。テストしやすくするためのリファクタリングもしない。扱わない

3. 90分の進め方（1コマ目 ＝ ex01）

ここに書くのは、6コマのうち1コマ目の90分です。2コマ目以降の進め方は、その回のSTEPを教科書に足すときに、この節へ表を足します。

STEPの区切り・見出し・目安時間は、教科書の各STEPの見出し（step-meta）に合わせています。教科書のSTEP構成や目安時間を変えたときは、この表も同時に直します。

STEP目安教員がすること終了時の確認
STEP 00 この単元のゴール5分完成の4行を読み上げる。「今日は文法を一から説明しない。JavaとSwiftとの違いだけを見る」と最初に宣言する。ゴールの4行を指させる。
STEP 01 Playground で動かす10分ブラウザで https://play.kotlinlang.org/ を開かせ、初期コードのまま Run を押させる。実行までに数秒かかることを先に伝える。10分で必ず切り上げる。全員のブラウザに実行結果の欄が開いている。
STEP 02 IntelliJ IDEA でプロジェクトを作る20分新規プロジェクトの表を1項目ずつ読み上げる。ビルドシステムが IntelliJ になっているかと保存先は、Create を押させる前に全員の画面を見て回る。作成後は、ウィザードが作った src/Main.kt をそのまま1回実行させる。そのあと ex01 パッケージと main.kt を作らせ、Main.kt を消させる。fun main() がクラスの外に書けることを、Javaの public static void main と並べて示す。（下の「STEP 02 で見る4つの場所」）src/ex01/main.kt の1行目が package ex01。自分で書いた1行がコンソールに出た。src の直下に Main.kt が残っていない。
STEP 03 val と var20分Javaの final、Swiftの let との対応表を先に見せる。「val は再代入禁止。中身が変わらないという意味ではない」を口で言う。println(name) に Yamada と Tanaka のどちらが出るかを予想させてからRunさせる。コンソールに 1 と Tanaka の2行。val がJavaの final・Swiftの let にあたると言えた。
STEP 04 数の型15分追加する2か所を指さして確認する。val number3: Float = 3.0 が通らないことを教員の画面で実演し、Swiftとの効き方の違いを示す。コンソールに4行。f の付け忘れがない。
STEP 05 ミニ練習10分練習A（3分）で val の変数と println を1行ずつ足させ、推論された型をマウスで確かめさせる。練習B（4分）で number1 = 5 を書き足させ、'val' cannot be reassigned を読ませる。最後の3分で、足した行を消して元の4行へ戻させる。練習A・Bを試し、エラーメッセージの意味を言えた。書き足した行が消えていて、出力が4行に戻っている。
STEP 06 完成10分4行の表を読み合わせ、val の行と var の行を指させる。同じ処理をJavaで書くと何行になるかを並べて比べる。保存先 Documents/Kotlin/K01HelloKotlin を言える。

目安時間の合計は 5＋10＋20＋20＋15＋10＋10 ＝ 90分で、1コマにちょうど収まります。ここには個別支援の時間を別に取っていません。クラスの進み具合に応じて、STEP 01の10分とSTEP 05の10分から先に削ります。STEP 03とSTEP 04の比較の時間は削りません。ここがこの回の本体です。

遅れている学生は、STEP 02（IntelliJ IDEA で自分のコードが動く）までの到達を優先します。ここまで届けば、残りは main.kt に数行足すだけなので、次の回の冒頭や合間に追いつけます。STEP 02が終わっていない状態で次の回に進むと、2コマ目の演習に入れません。ここだけは全員そろえてから終わります。進みが速い学生には、val の行を var に変えたら警告が出るか、という確認を渡します。

JDKの欄が空のまま作ってしまった学生は、STEP 02の実行に進めません。STEP 02の見回りで早く見つけ、欄を開いて出てきたものを選ばせます。それでも動かない間は、Playgroundで続きのコードを書かせます。

STEP 02 で見る4つの場所

プロジェクトの新規作成は、6コマのうち1コマ目のこの1回だけです。ここで形を間違えると、残り5コマぶんの画面と手順が教科書と食い違い、毎回その学生だけ別の説明が要ります。新規プロジェクトの画面で見るのは、次の4か所です。項目名は日本語表示の IntelliJ IDEA のものです（教科書STEP 02の画面と同じ）。

画面の項目選ばせる値違う値で作るとどうなるか
ビルドシステム（英語表示では Build system）IntelliJここが最重要です。Gradle で作ると、ビルド設定ファイルと同期待ちが増え、フォルダの形も src/main/kotlin に変わります。以降の「src を右クリックしてパッケージを作る」手順と画面が、そのまま食い違います。Maven も同じ理由で選びません。
サンプルコードの追加（英語表示では Add sample code）ONのまま（既定）OFFにすると src が空の状態で始まります。自分のコードを書く前に1回動かす、という足場がなくなります（下の「サンプルコードを1回動かしてから消させる」）。
コンパクトなプロジェクト構造を使用するONのまま（既定）OFFにすると src/main/kotlin という深い形になり、教科書の画面（src の直下に Main.kt）と食い違います。パッケージを作る場所も変わるので、学生が自力で読み替えられません。

見回りは、上から順ではなく、ビルドシステムから見ます。ここだけは作り直しになるためです。1列目を指で追いながら「ビルドシステムは？」と全員に聞き、IntelliJ が選ばれている画面を確認してから Create を押させます。押したあとに気づいた場合は、できたプロジェクトを閉じ、フォルダごと消して作り直させます。

JDKの欄に出る名前は、Macによって変わります。版は板書しません。教科書も「一覧に出ているものを、そのまま使います」と書いています。見るのは、欄が空になっていないかだけです。空の学生には、欄を開いて出てきたものを選ばせます。候補が1つも出ないMacは、その場では直せないことがあるので、Playgroundで続きを書かせ、授業後に環境を確認します。

サンプルコードを1回動かしてから消させる

「サンプルコードの追加」をONのままにして、学生が自分でコードを書く前に、ウィザードが作った src/Main.kt を1回実行させます。ねらいは、動く状態から始めることです。

  • 動く状態を1回見ておけば、そのあと動かなくなったときに疑う場所が自分が書き換えた行だけになります。空のプロジェクトから始めると、JDKの選択・実行構成・書いたコードのどれが原因かを切り分けられず、質問が「動きません」で止まります。
  • 実行の操作（fun main() の左の緑の三角 ▷ を押し、「'MainKt' の実行」を選ぶ）を、自分のコードで失敗する前に覚えられます。操作とコードの2つを同時に疑わせないための順番です。
  • サンプルコードは fun main() がクラスの外に書かれた形です。Javaの public static void main と並べて見せる材料に、そのまま使えます。

1回実行して出力が出たことを全員で確認したら、src に ex01 パッケージを作らせ、その中に main.kt を作らせます。そのうえで、ウィザードが作った src/Main.kt を右クリックし、「削除」で消させます。（教科書⑥の手順の順番です。）ここから先が、教科書の完成コードと同じ置き場所です。

サンプルコードには for と文字列テンプレート（$i）が入っていますが、中身の説明はしません。「これは最初から入っている見本で、今日は消します」で足ります。for は ex05 / ex06 の回、文字列テンプレートは ex02 以降の回で扱います。質問が出たら、その回の予告として1文で答えます。

消し忘れた Main.kt が src の直下に残っていると、あとで実行構成の一覧に MainKt が2つ並び、どちらを実行したのか分からなくなります。STEP 02の終わりの見回りで、src の直下が ex01 だけになっているかを見ます。

5. Java / Swift 経験者が躓きやすい点

ここに挙げるのは、プログラミングが初めてだから起きることではなく、JavaとSwiftを知っているから起きる間違いです。見回りで探す対象もこの表にそろえます。

症状原因（どの言語の癖か）その場での直し方
val を「中身まで変わらないもの」だと説明してしまう / そう受け取るJavaの final と同じで、再代入が禁止されるだけ。参照先のオブジェクトの中身は変えられる。Swiftの let は構造体では中身も変わらないため、Swift側の感覚とずれる。「val は名前の付け替えを禁止する。箱の中身の話ではない」と言い直す。この単元の値は数と文字列だけなので差は出ない。実際の差はコレクションを扱う ex10 の回で見せる、と伝えて先へ進む。
val number3: Float = 3.0 と書いて、赤いエラーが出るSwiftでは型注釈を書けばリテラルがその型になる。Kotlinでは 3.0 は Double のままで、Float へ暗黙に変換されない。3.0f と書かせる。「型を書けば合わせてくれる」のではなく「リテラルの書き方で型が決まる」という順序に直す。教科書STEP 04の比較表を一緒に読む。
f を付けずに Float のつもりで進み、型が Double になっているJavaでも float f = 3.0; はエラーだが、Kotlinは型を書かないのでエラーにならず通ってしまう。number3 にマウスを重ねて、推論された型を画面で見せる。出力の 3.0 だけでは見分けが付かないことを伝える。
行末にセミコロンを付けているJavaの癖。Kotlinはセミコロンを許容するのでコンパイルが通ってしまう。IDEの設定によっては弱い警告が出ることはあるが、赤いエラーにはならないため、指摘しなければ癖が残る。付けさせる練習はしません。教科書STEP 03のPOINT「Swiftと同様に文末のセミコロン（;）が不要です」をその場で読ませます。見回りで残っているのを見つけたら消させ、消しても動くことを1回実行して見せる。Swiftも不要だった、と対応付けると残りやすい。以降の回でも、見回りでセミコロンを探す。
class Main { public static void main(String[] args) { … } } の形を作ろうとするJavaの癖。Kotlinの fun main() はクラスの外（トップレベル）に書ける。Kotlinクラス/ファイル の一覧で ファイル を選び直させる。クラス を選んでできたファイルは消させる。クラスは ex04 の回で扱うと伝える。
System.out.println(…) または print(…) と書く前者はJavaの癖、後者はSwiftの癖。Kotlinの print は改行しないので、出力が1行につながって「4行出ない」という症状になる。println に直させる。print と println の違いは、1回実行して見せるほうが早い。
int number1 = 1; のように型を先に書くJavaの癖。Kotlinは val 名前: 型 = 値 の順で、Swiftと同じ並び。Swiftの書き方を思い出させる。この回では型注釈そのものを書かせないので、val number1 = 1 に直させる。
Kotlinの var を、Javaの var（型推論）と同じものだと考えるJava 10以降の var は型を書かないという意味で、再代入はできる。Kotlinの var / val は再代入できるかどうかの区別で、型推論は両方に効く。「Kotlinでは型推論は既定で効いていて、var / val はそれとは別の話」と1文で整理する。val number1: Int = 1 も書けることを口で言うにとどめる。
ビルドシステムが Gradle のままプロジェクトができている画面を読まずに Create を押した。Androidの経験がある学生ほど、Gradleを見て「これでよい」と思いやすい。できたプロジェクトを閉じ、フォルダごと消して作り直す。Createを押させる前の見回りで防ぐ（「3. 90分の進め方」の「STEP 02 で見る4つの場所」）。
src の下が main/kotlin という深い形になっている「コンパクトなプロジェクト構造を使用する」のチェックを外して作った。教科書の画面（src の直下）と食い違うので、作り直す。src/main/kotlin のままでも動くが、以降5コマぶんの手順が読み替えになるため、1コマ目のうちにそろえる。
ウィザードが作った src/Main.kt が残っている1回実行したあと、消す手順を飛ばした。右クリック → 削除 で消させる。残っていると実行構成に MainKt が2つ並び、どちらを実行したのか分からなくなる。
src の直下に main.kt を作っているパッケージを作る手順を飛ばした。ex01 を作り、main.kt をドラッグで移動する。1行目が package ex01 になることを一緒に確かめる。
緑の三角（▷）が出ないfun main() のつづり違い、または () の抜け。教科書のコードと1文字ずつ照合する。Main や mian がないか見る。
実行しても何も起きないJDKが選ばれていない（欄が空のまま作った）。プロジェクトの設定でJDKを選び直させる。候補が1つも出ないMacは、その場で直せないことがあるので、Playgroundで続きを書かせ、授業後に環境を確認する。
赤い波線が消えない全角スペース、全角の引用符、全角のかっこが混ざっている。入力が英数字になっているか確認し、その行だけを消して打ち直させる。
完成チェックで動かないSTEP 05の練習で書き足した行（練習Aの2行、練習Bの number1 = 5）を消していない。書き足した行を探して消す。最後の3分を必ず取る。

チェックの保存はブラウザのlocalStorageを使い、送信はしません。ブラウザ・ファイルの移動・保存設定で記録が消える場合があるため、成績や提出の記録には使わないでください。到達度は、上の表の4つの証拠を授業内で確認します。

10. 提出課題（APK）の案内

この授業の提出課題は、自分で作ったAndroidアプリを1つ選び、アレンジを加えて、APKというファイルにして提出することです。提出するのは1つだけです。新しいアプリを一から作らせるのではなく、授業で自分の手で動かしたアプリを1つ選ばせ、そこに自分で決めた変更を加えさせます。

この単元 K01HelloKotlin は、提出課題の対象にはなりません。純Kotlinのコンソールアプリで、Androidアプリではないためです。学生から「これを提出するのですか」と聞かれたら、そう答えてください。提出の対象になるのは、後半のAndroid系の単元（A01〜）で自分が作ったアプリです。

学生からの質問答え方
今日作った K01HelloKotlin を提出するのか提出しない。この単元に提出物はない。純Kotlinのコンソールアプリなので、APKにならない。
何を提出するのか後半のAndroid系の単元で自分が作ったアプリから1つ選び、アレンジを加えてAPKにする。
そのまま出してよいのかアレンジを加えたものを出す。どこを変えたかを自分の言葉で説明できるようにしておく。
いつ案内があるのかAndroid系の単元に入ってから、共通資料を使って案内する。今日は「あとで案内する」で足りる。

APKの作り方と提出の手順は、共通資料の 提出課題とAPK（docs/common/apk.html）にまとめています。学生には教科書のサイドバーから開かせてください。この教員用ガイドからは ../../docs/common/apk.html で開きます。

提出先と締め切りは、共通資料には書いていません。教員が授業で案内します。年度やクラスで変わるため、教材には書かない方針です。
