2. この単元の教材方針

この単元の主題は「Kotlinという言語を初めて書く」ことです。プログラミングの入門ではありません。受講生はすでに Java と Swift を書けるので、同じことを Kotlin ではどう書くか、そこで何が変わったかに集中させます。教科書の各STEPには、Java か Swift（または両方）との比較を必ず置いています。

Kotlinパートを、単元に分けずに1つにした理由

Kotlinの文法は、K01HelloKotlin という単元1つ、プロジェクト1つ、教科書1冊で、6コマかけて進めます。「変数」「Null安全」「クラス」…と単元を分け、そのたびに新しいプロジェクトを作らせる形にはしていません。理由は3つです。

  • ウィザードの操作で時間が消えるからです。1コマで書くコードは十数行です。それなのに毎回プロジェクトを新規作成させると、90分のうち15〜20分が新規プロジェクトの操作と最初のビルド待ちに消えます。比較に使う時間がそのぶん減ります。
  • 前に書いたコードを見返せるからです。同じプロジェクトに ex01、ex02 …と並ぶので、「先週の val の行と見比べて」と、画面の中だけで指示できます。別プロジェクトだと、開き直す操作から説明することになります。
  • 前年度の資料と同じ形だからです。前年度も1つの HelloKotlin プロジェクトに、節ごとのファイル（Main01、Main02 …）を足していく形でした。今年はファイルの代わりに src/exNN/ のパッケージを足します（「7. 前年度の資料（PDF）との対応」）。

この決め方の結果として、2コマ目以降は「新しいプロジェクトを作る回」ではなく「同じプロジェクトを開き直す回」になります。1コマ目の STEP 02（プロジェクトの新規作成）は、6コマで1回だけです。ここで作った場所（Documents/Kotlin/K01HelloKotlin）を学生がFinderで開けるようにしておくことが、2コマ目以降の授業時間を守ります。

2コマ目（ex02 ＝ Null安全）の教材方針

2コマ目の主題は Null安全です。K01の6コマで扱う項目のうち、Javaに対応物がないものは2つしかなく、そのうちの1つがこれです（もう1つは ex07 の拡張関数）。一方でSwiftのオプショナルとはほぼ同じ発想です。そこでこの回は、Javaとの比較で「Javaではこうは書けない」を見せ、Swiftとの比較で「知っているあれと同じ」を見せるという組み立てにしています。片側だけで説明すると、Javaしか思い出さない学生には新概念に、Swiftしか思い出さない学生には「知っている話」になって、どちらも90分が余ります。

方針理由授業での扱い
この回に出す記号は ? と ?. の2つだけにするNull安全に関わる記号はほかにもあるが、1回で複数を並べると、どれがどの役目かが混ざる。完成コード K01HelloKotlin/src/ex02/main.kt は、この2つだけで最後まで書けている。学生から !! や ?: の質問が出たら、記号を板書せずに「あとの回で扱う」で止める（下の「この2コマ目で意図的に扱わないこと」）。

5. Java / Swift 経験者が躓きやすい点

ここに挙げるのは、プログラミングが初めてだから起きることではなく、JavaとSwiftを知っているから起きる間違いです。見回りで探す対象もこの表にそろえます。

1コマ目（ex01）

症状原因（どの言語の癖か）その場での直し方
val を「中身まで変わらないもの」だと説明してしまう / そう受け取るJavaの final と同じで、再代入が禁止されるだけ。参照先のオブジェクトの中身は変えられる。Swiftの let は構造体では中身も変わらないため、Swift側の感覚とずれる。「val は名前の付け替えを禁止する。箱の中身の話ではない」と言い直す。この単元の値は数と文字列だけなので差は出ない。実際の差はコレクションを扱う ex10 の回で見せる、と伝えて先へ進む。
val number3: Float = 3.0 と書いて、赤いエラーが出るSwiftでは型注釈を書けばリテラルがその型になる。Kotlinでは 3.0 は Double のままで、Float へ暗黙に変換されない。3.0f と書かせる。「型を書けば合わせてくれる」のではなく「リテラルの書き方で型が決まる」という順序に直す。教科書STEP 04の比較表を一緒に読む。
f を付けずに Float のつもりで進み、型が Double になっているJavaでも float f = 3.0; はエラーだが、Kotlinは型を書かないのでエラーにならず通ってしまう。number3 にマウスを重ねて、推論された型を画面で見せる。出力の 3.0 だけでは見分けが付かないことを伝える。
行末にセミコロンを付けているJavaの癖。Kotlinはセミコロンを許容するのでコンパイルが通ってしまう。IDEの設定によっては弱い警告が出ることはあるが、赤いエラーにはならないため、指摘しなければ癖が残る。付けさせる練習はしません。教科書STEP 03のPOINT「Swiftと同様に文末のセミコロン（;）が不要です」をその場で読ませます。見回りで残っているのを見つけたら消させ、消しても動くことを1回実行して見せる。Swiftも不要だった、と対応付けると残りやすい。以降の回でも、見回りでセミコロンを探す。
class Main { public static void main(String[] args) { … } } の形を作ろうとするJavaの癖。Kotlinの fun main() はクラスの外（トップレベル）に書ける。Kotlinクラス/ファイル の一覧で ファイル を選び直させる。クラス を選んでできたファイルは消させる。クラスは ex04 の回で扱うと伝える。
System.out.println(…) または print(…) と書く前者はJavaの癖、後者はSwiftの癖。Kotlinの print は改行しないので、出力が1行につながって「4行出ない」という症状になる。println に直させる。print と println の違いは、1回実行して見せるほうが早い。

2コマ目（ex02 ＝ Null安全）

この回の躓きは、Java経験から来るものとSwift経験から来るものが、はっきり分かれます。Java側は「書けてしまうはずの行が書けない」、Swift側は「考え方は同じなのに、つづりと呼び方が違う」です。どちらの症状かが分かれば、かける言葉も変わります。

症状原因（どの言語の癖か）その場での直し方

var name2: String? = nil と書いて、nil が見つからないというエラーになるSwiftの癖。考え方は合っている。Kotlinでのつづりが null だというだけ。null に直させます。ここは「Swiftと同じ考え方で合っています」と先に認めてから、つづりだけ直させます。間違いとして扱うと、せっかく対応付いている理解をほどいてしまいます。
var name2: String = null と書いて、コンパイルエラーになる型のうしろの ? を付け忘れた。var にすればnullを入れられる、と読み違えている。「val と var は再代入できるかの区別、? はnullを入れられるかの区別で、別の軸です」と整理します。1コマ目の val / var の表と並べて見せると早いです。
name2.count() と書いて（? なし）、コンパイルエラーになるJavaの癖。Javaでは name2.length() と書けてしまい、name2 がnullなら実行時に落ちる。name2?.count() に直させます。「Javaならこの行は書けます。書けたうえで、動かしたときに落ちます」と言い、Kotlinが落ちる場所を書いた時点へ前倒ししたことを、この行で見せます。
?. の戻り値が Int? だと気づかず、そのまま計算しようとする（name2?.count() + 1 など）Swiftでも同じエラーになるが、Swiftでは ?. の結果がオプショナルになることを意識せずに書けてしまう場面が多く、Kotlinで初めて止まる。name2?.count() にマウスを重ねて、型が Int? と出ることを画面で見せます。「?. を1つ通ると、結果にも ? が付きます」と言います。ここで ?: や !! を教えて解決しないでください（この回では扱いません）。今日は println にそのまま渡すところまでで止めます。
name2?.count と、かっこを付けずに書くSwiftの癖。Swiftの count はプロパティなのでかっこが要らない。Kotlinでは count() が関数なので、かっこを付けさせます。「Swiftの count にあたるのは、Kotlinでは length のほうです」と添えると対応が付きます。
